## 0. Why this exists

The prior system failed partly because work raced ahead of understanding: ambitious multi-phase plans, half-executed, pivoted mid-flight, documented at the end. This time we expand slowly and on-disk. Each stage produces a durable artifact and stops for user sign-off before the next begins.

---

## 1. The stages

```
[S0 Rough design] ──▶ [S1 HLD] ──▶ [S2 LLD] ──▶ [S3 Dev + Tests] ──▶ [S4 HITL] ──▶ (next component)
      ▲ gate            ▲ gate       ▲ gate          ▲ gate              ▲ gate
   user signs        user signs    user signs     user signs          user signs
```

Each stage, its exit artifact, and its gate:

| Stage | Produces | Exit gate (user confirms) |
|---|---|---|
| **S0 — Rough design** | `DESIGN-v4.md` — problems, primitives, artifacts, transitions, roles, microservice set. | "The shape is right. Proceed to HLD." |
| **S1 — HLD (High-Level Design)** | One HLD doc per component: responsibilities, public interface (the ABC it implements), dependencies, data it owns, failure modes, the contract tests it must pass. No code. | "The component boundaries + interfaces are right. Proceed to LLD." |
| **S2 — LLD (Low-Level Design)** | One LLD doc per component: module layout, function signatures, schemas (Pydantic), state-transition logic in pseudocode, error codes, the test list (unit + contract). No code. | "The internals are right. Proceed to build." |
| **S3a — Dev** | The component implemented in its own repo per the LLD. | (internal; flows to S3b) |
| **S3b — Refactor** | Code reviewed & refactored: hard-coded values → named constants; recurring literals/states → enums where they earn it; repeated shapes → interfaces/ABCs where they earn it. A short `X-REFACTOR.md` records what changed and why. **Always runs before S3c.** (User directive 2026-05-16.) | "Refactor is right. Proceed to tests." |
| **S3c — Tests** | Unit + contract tests per TESTPLAN, all green; static gates pass. | "Code + tests are right. Proceed to HITL." |
| **S4 — HITL / Acceptance** | Two shapes depending on the component: **(a) internal / non-interactive component** (libraries like `edp-contracts`, schemas, deterministic tools) — the green automated suite IS the evidence; the user reviews the S3c result + summary and gives a verdict. No manual reproduction ritual. **(b) user-facing behavioural component** (the neuron/recipe/plan flow, anything the user actually drives) — the user exercises it end-to-end by hand. The methodology picks the shape per component; don't manufacture a manual ritual for a contracts package. | "It works / accepted. Proceed to the next component." |

**Discipline:** we do S1–S4 *per component*, not all-S1 then all-S2. One component walked fully from HLD to HITL before the next starts. (Exception: the three base contracts in §3 are built first, once, because everything depends on them.)

## 3. Build order (proposed; user confirms at S0 gate)

The standardization mandate (DESIGN-v4 §13) forces this order:

1. **Base contracts** (`Microservice` ABC, `Skill` contract, `Tool` contract, broker envelope, error envelope). These are tiny and everything depends on them. HLD+LLD+tests for the contracts themselves.
2. **`eda-base/claude/`** skeleton — the MCP tool surface (12 tools), the slash-command activators (neuron/planner/worker ~30 lines each), the skill set (ocak + leaves + goal-keeper + critic), recipe/plan schemas, `next_action` deterministic Python path. No microservices yet — `pool.spawn_*` and `broker.send` are stubbed to local no-ops so one recipe can be walked on paper-in-code.
3. **`eda-base/edp-broker/`** — the dumb message bus.
4. **`eda-base/edp-pool/`** — shell spawner, session↔role↔handle map, lock-by-spawn, worker-liveness heartbeat, max-workers=3 with verbatim error propagation.
5. **`eda-base/edp-fsm/`** — the masked-LLM behind `next_action`'s nuanced path.
6. Integration: one full recipe (the §7 walkthrough in DESIGN-v4) executed end-to-end across real shells.
7. Deferred: `edp-memory-svc`, `edp-proxy`, `edp-trace-viewer`, ML — only if/when needed (DESIGN-v4 §5).

Each numbered item walks S1→S4 before the next begins.

## 4. Per-component documentation convention

For component `X`, on disk under `eda-base/claude/docs/design/components/X/`:

- `X-HLD.md` — written at S1, frozen at the S1 gate.
- `X-LLD.md` — written at S2, frozen at the S2 gate.
- `X-TESTPLAN.md` — the test list, written at S2, executed at S3.
- `X-HITL.md` — the user's behavioural smoke script + the user's sign-off note, at S4.

The component's *code* lives in its own repo (`eda-base/X/`); the *design docs* live in `claude/docs/design/components/X/` so they survive even if a microservice repo is reset.

---

## 4a. TODO discipline (user directive 2026-05-17)

Deferred/seam work is marked in-code as `# TODO(<owner-or-component>, <why>)`.
TODOs are taken up at **two** moments, not "eventually":
1. At **S3b Refactor** of the component that owns them — the refactor pass sweeps and resolves or explicitly re-defers every TODO with a reason.
2. **Whenever discovered during related implementation** — if building component X you hit a TODO that X's work now makes resolvable, resolve it then, don't walk past it.
A component cannot pass S3b with un-triaged TODOs (resolve, or re-defer with an explicit owner+reason logged in its REFACTOR.md).

## 5. Rules that bind every stage

1. **On-disk only.** No design or context in the memory layer. Memory holds collaboration rules only.
2. **No gate skipping.** S(n+1) does not start until the user signs the S(n) gate. If tempted to "just start coding," stop and ask.
3. **Standardize before scaling.** A component cannot be built (S3) unless it implements its base contract (§3 item 1 must be done first).
4. **Document as you go.** The stage artifact is written *during* the stage, not after. Late documentation was a named root cause of the prior failure.
5. **Impact analysis on every change.** Any change to an already-built component requires an impact-analysis note in that component's docs folder before the change is made.
6. **PROGRESS.md is the running log.** Every gate pass, every stage entry, is logged there with date + actor.
