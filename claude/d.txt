● Let me think through this before declaring outcomes. There are some real
  architectural tensions worth surfacing.

  Real goal: Hand-off a PWA's current state (app version +
  IndexedDB/localStorage) from PC to iPhone, so a non-tech friend can continue
  using it offline on the go.

  Key tensions I see:

  1. "Just a Firefox extension" understates the iPhone side. iOS gets no app —
  fine — but it still has to receive the data somehow. A browser extension
  cannot push data into iOS Safari's storage directly. The iPhone has to visit a
   URL that hydrates its own IndexedDB/localStorage. So either (a) the PWA
  itself must include a "sync receive" page, or (b) data goes through a relay
  server / QR codes.
  2. Cross-origin storage: the extension on PC can read the PWA's IndexedDB only
   by injecting a content script into the PWA's origin. That works, but means
  the extension must know the PWA's URL.
  3. Transport options — each has real trade-offs:
    - QR code(s): zero infra, but IndexedDB can easily be megabytes → chunked QR
   codes are slow/painful.
    - Local WiFi (extension hosts a temporary URL via service worker / WebRTC):
  fast, but signaling is awkward.
    - Cloud relay (paste/upload, iPhone downloads): simplest UX, but needs a
  server.
    - WebRTC with QR-code signaling: no server, fast — but requires the PWA to
  embed the receive logic.
  4. The PWA-receive side is unavoidable. Whichever transport, the PWA itself
  needs a receiver page that knows how to hydrate its own IndexedDB. The Firefox
   extension alone can't do this without cooperation from the PWA.

  outcomes.

● I have to push back on a load-bearing assumption before going further.

  Critical fact: Firefox on iOS does not support WebExtensions like Firefox
  desktop/Android does. Apple requires iOS browsers to use WebKit, and Firefox
  iOS is effectively a WebKit shell with no add-on/plugin support comparable to
  desktop. Mozilla's own docs confirm this. iOS 26 has loosened things for
  Safari WebExtensions, but Firefox iOS still doesn't support the desktop-style
  extension API. So "install the same plugin on iPhone Firefox" is not a path
  that exists today.

  This actually doesn't break your goal — it just changes the shape of the
  solution:

  What does work:
  - Firefox extension on PC reads the PWA's IndexedDB/localStorage/Cache via a
  content script (the extension knows the PWA's origin).
  - iPhone side has no extension. Instead, the PWA itself includes a small
  "sync-receive" route (e.g. /sync). When the friend opens that URL on iPhone
  Safari, the PWA's own JavaScript writes its own IndexedDB/localStorage/Cache
  from the incoming payload — fully legal because it's same-origin.
  - Transport between them = your earlier WiFi/QR-code preference, no server
  needed:
    - QR code carries a short WebRTC signaling handshake (few hundred bytes)
    - WebRTC datachannel then streams the actual MB-sized payload PC→iPhone
  directly over LAN/internet

  So the architecture is:
  1. Firefox extension (PC) — UI to pick a PWA tab, extract storage, show QR.
  2. JS receiver library — small drop-in for the PWA author; renders a /sync
  page on the PWA that scans QR / opens WebRTC and rehydrates storage.
  3. Demo PWA — proves the round-trip works.

  Cookies and Service Worker / Cache hydration on iOS Safari are the trickiest
  parts — Cache Storage you can populate from JS; cookies cannot be written from
   JS for HttpOnly flags but normal ones can be.

  Sources:
  - Add-ons in Firefox for iOS - Mozilla Support
  (https://support.mozilla.org/en-US/kb/add-ons-firefox-ios)
  - Can I install add-ons in Firefox iOS mobile? - Mozilla Support
  (https://support.mozilla.org/en-US/questions/1102830)
  - Extensions on Firefox for iOS 18 - Mozilla Support
  (https://support.mozilla.org/en-US/questions/1486487)
  - Apple's iOS 26 Safari WebExtensions change - MacObserver (https://www.macobs
  erver.com/news/apple-just-made-a-huge-change-to-safari-extensions-on-iphone/)
